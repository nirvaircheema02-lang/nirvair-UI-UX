01 / The big picture

Fix the selected issue. Preserve the page.

Fix & Redesign Agent uses a reviewed Audit Agent run to apply authorized Design System fixes and generate a React preview for review.

→

Deliverable

React preview + Figma bundle

Runnable source, localhost URL, measured verification and a Figma copy of the same page.

Targeted changes

A finding marked Fix authorizes its required correction, not a redesign of the surrounding section.

11 named pipeline stages

R1–R8, C2 mapping, B1 behavior capture and the RV Resolver. Four stages can request judgment (C2, RV, R3, R5); in this setup they are answered automatically. These are not eleven independently running AI agents.

Component agents disabled

The L-series exists in code, but the current CLI blocks component-building and publishing routes.

This HTML is a learning guide. It does not run a redesign. The agent’s actual deliverable is a generated React app.

What each mode contains
Selected sections
Only sections containing a selected Fix finding. Each section remains complete and in original order. Unselected sections are absent.
Full page
Every page-specific content section, including unchanged sections. This mode does not authorize extra fixes.
Both modes exclude the global header and footer. Paths are already configured.


Before starting
A missing Fix Plan or conflicting run identity must be resolved. Zero or multiple matching runs require an exact choice.
This project’s configuration turns on deterministicJudgments: RV, R3, R5 and C2 are answered from their own prompts, so a run reaches G2 without pausing for a session. The answers never invent a design decision, and each one says it came from this mode. Without that setting the default provider is claude-session, which expects the active Claude Code session to answer the judgment bundles. The optional anthropic-api provider makes direct API calls. The L-series component judgments would still pause.


03 / How agents connect
One pipeline, two preview scopes.
The implementation is a file-backed, resumable state machine. These graphs explain its execution; this project does not use Audit Agent’s custom graph engine.







Execution / outputDependency, pause or correctionYour decision


What the shared resources do
DS registry: expected colors, typography, components, variants and rules.
Runtime logic: mapping, edit guards, scope, resolved targets, measurements, the design baseline and saved decisions.
Style rules: structural DS rules in the generator, plus the shared and per-project user style rules.
Input example: the registry supplies suitable input styles; runtime rules keep the edit on the selected field and measure its result. These are resources, not extra autonomous agents.


The correction loop


C2, RV, R3 and R5 judgments are answered automatically when deterministic mode is on; otherwise a session answers them. G1 is conditional on conflicts; G2 requires your decision. Resume restores the saved capture, targets and budget usage; it is not guaranteed to continue at an arbitrary browser instruction.


Where work is reused
The page is captured once and frozen. The behavior baseline and the design baseline are written once. Resolved targets are derived once and read by R3, R4, R5 and R8. The correction budget persists across resume and regenerate.
Why it does not loop
One R3 → R4 → R5 pass by default here, judgments answered without a pause, and a single correction budget after the preview exists. The route still runs stages in order with no page-worker fan-out, and no speed multiplier is claimed.

05 / How Fix JSON is understood
The decision selects. The finding explains.
fix-plan.json stores your decisions. data.json contains audit evidence and expected values. The agent joins them by findingId and maps the finding to the captured page.


1 · Validate identity
Check schema and source run ID. A Fix Plan belonging to another run is refused.
2 · Join the evidence
Retrieve the section, mismatches, rules, DS candidates and evidence. Unknown IDs are reported; duplicate IDs use the last decision.
3 · Locate the element
C2 checks candidates and stamps a target. Ambiguous or absent mapping does not authorize an arbitrary edit.


Decision and classification are different
decision: fix is your instruction. NEEDS_REVIEW is the audit’s uncertainty. A selected uncertain finding needs a grounded design decision.
Illustration only; your Fix Plan is unchanged. A finding with no decision stays undecided.


When the audit does not prescribe the design


The Resolver’s execution boundary
The Design Review Resolver is node RV, an executable stage that runs before R3. Each unresolved property ends as a resolved target, a preserve existing decision or an unresolved gap with its specific reason. The result is context/resolved-targets.json; the audit’s data.json is never edited.
R3 plans, R4 applies and R5 and R8 measure the same targets, each in its own state (default, hover, keyboard focus). An edit of a property that is not a target is refused. Colours come only from DS tokens, exact first, then the nearest suitable one; a reference project’s raw colour is never used.
The session reference below still describes how residual design questions are answered. Choices are reuse-existing, compose-existing, propose-variant, preserve-existing or unresolved; authored entries in context/design-decisions.json bind the Resolver. R4’s component-swap adds classes; it does not mount a React component, and unsupported work stays explicit.

07 / What must stay unchanged
Local fixes, preserved composition.
These persistent user rules apply to every generated preview and hand-authored override, not just one earlier page.


Preserve composition
Keep section order, columns, card grouping, content, assets, alignment and responsive behavior unless the selected finding or an explicit instruction requires that exact change.
A centered heading or form stays centered.
Preserve interactions
Capture sticky pin/release, scrolling, hover/focus, controls and keyboard interactions before editing. A screenshot cannot prove behavior.
Unreproduced JavaScript behavior must be reported.
Use the red primary action
Primary actions use DS Button brand and its red shimmer token. The black primary variant is prohibited.
Other suitable variants remain available; do not turn every option or link into a red CTA.
Derive missing local variants
Reuse suitable DS components first. Missing treatments for selected controls may use existing DS tokens, with states and rationale recorded.
They remain local proposals, not automatic additions to the shared DS.


Locked for every page
These came from work on the survey pages. They live in the generator, the template or the shared rules file, so a new project gets them without being asked again.
Typography and colour
“Step NN” labels are not upper-cased and stay small (2xs). Stat numerals use the DS type-scale step and the neutral ink --black-900, never brand red, with no hover colour change, and count up once when scrolled into view (reduced motion shows the final value). Brand red is for CTAs only.
The site’s own text ink #141016 is not a DS colour: text takes --black-900 in every section.
Structural DS rules
An unmapped “Read More ↗” link is the DS CTALink. An unmapped brand-red link box is Button brand. A small pill chip is the DS Badge. An eyebrow label drops its decorative icon and takes the DS SectionLabel style. Carousel indicators use DS colours and 24×3 bars. A section keeps its own vertical spacing.
Same section, same design
FAQs have no fill behind the question rows. Our Resources “Read now” takes the DS on-dark link ink. Testimonial author name and role take --text-xs and --black-900. Our Impact’s “Read More ↗” is right-aligned. The numbered 01–0N cards have square corners, with their hover overlay.
Card hover group
While the pointer is on a numbered card, the other cards fade to 20% and the hovered card stays fully visible, as on the live site. Mouse only; part of the preview template.
Two kinds of user style rules
user-style-rules.shared.json at the repo root holds an instruction that is true of a section on every page; section: * means every section of the page. projects/<project>/user-style-rules.json holds what is true of one page only, and may not use *. An id cannot be in both files.
Values are limited to 0, none, transparent, currentcolor, 1px, a var(--token) and two alignment keywords. A rule that matches nothing is reported, and an element named by several rules keeps all of them. R8 measures the user’s value instead of the audit’s target and records the difference as intentional, only for the properties the rule names.

Guards have limits. R3/R4 check explicit edits; they are not complete CSS interpreters. Arbitrary classes, aliases, dynamic behavior and composition still need rendered verification.


Token choices and intermediate DOM edits
An R3 edit carries its resolved target’s value. For a finding that has resolved targets, a colour-bearing edit is accepted only as that value, as var(<target token>), or as a DS token that is the same colour. Raw colours, named or system colours, unknown var()s and Tailwind arbitrary-value colour classes are refused, as are injected declarations.
An intermediate edit on the captured website may still hold a resolved literal, because that page does not define DS variables. The guard checks it against the token, not against its spelling.


08 / Verification & saved evidence
Read the measurements behind the verdict.
Run status, R5 comparison, R8 preview verification and per-finding accounting answer different questions.


ResultMeaning
Run statusCompleted, failed, blocked, awaiting judgment or awaiting approval.
R5 · PASS / PARTIAL / FAILApplied edits, structural preservation and the recorded visual verdict. With deterministic judgments it reports every finding UNCERTAIN and leaves the verdict to R8.
R8 · Overall preview statusPASS, FAIL or INCOMPLETE, identical in verification.json, pv-status.json, the preview bar, PREVIEW.md, the CLI and G2.
Finding accountingMeasured fixed, DS-component verified, preserved, unresolved or not represented—with reasons.


What R8 measures
Scope and content
Expected sections and order, text, links, loaded images, headings and section height.
Targets and styles
Every resolved target, read from the rendered page in its own state (default, hover, keyboard focus), plus typeface rules and contrast.
Fidelity to the original
The original’s default, hover and focus styles, columns, grouping, order, alignment and sticky pin/release are captured once, before any edit, and compared under the same conditions. Only a change a target authorizes may differ.
Behavior and runtime
Interaction comparison with the original, browser errors, remote requests and overflow, on desktop and mobile.


A saved run, not a fresh test


Verified, failed and unverified stay separate. A required check that could not be verified makes the status INCOMPLETE, never PASS, and a finding is called fixed only when it was measured. Read the counts and the first gaps.


What a status does not tell you
Optional or by-design limitations (the :active and disabled states, script-driven states, hover on mobile, island internals) are listed as disclosed and never change the status. R8 does not run the original website’s scripts; native and CSS behavior and supported adapters work, other widgets can need an override. Form submission is simulated, and a simulated or not-reproduced behavior is labelled before approval is asked.
A preserve decision is called preserved only when the same element, property, state and viewport were compared on both pages and agree; anything the verifier could not compare is unverified with a reason.



G2 is your decision
Review the URL, source and verification. A FAIL needs explicit acceptance of the failed checks; an INCOMPLETE can be approved, and the recorded note names the unverified requirements you accepted. Approval is bound to the targets, baseline, fidelity report and correction outcome, so changing any of them invalidates it. The agent must not approve on your behalf.


09 / Figma export
The same page, as editable Figma layers.
The React preview stays the deliverable. After R8 builds it, the agent prepares a bundle that a session pushes into the audit run’s own Figma file as a page named Fix & redesign page.


1 · Prepared by R8
figma-export/
Built from the final preview, about 20 seconds, no pipeline rerun.
→
2 · Pushed by a session
use_figma
The steps are in FIGMA_EXPORT.md; the pipeline cannot call Figma itself.
→
3 · Checked
Against the preview
Screenshot comparison and checksums before it is reported.


What it reads
The run’s built preview-app/dist, served locally. Each section is scrolled into view and measured, so the file shows the rendered page, not the source.
The target file is the audit project’s own Figma file (its key is read from the audit project). The Design System file is read-only and is never built in.
How faithful it is
Real pictures, not placeholders (SVG pictures rasterised, a video becomes its most detailed frame). Editable layers with auto-layout where the measured geometry reproduces it. DS Button instances for brand CTAs. A pinned section with a long scroll runway is built as one viewport. Hover and animation states are not part of the export.
Tokens, never a redesign
Colours bind to the Ken / Colors variables: exact match first, then the nearest suitable token, then the closest of the same alpha within a small distance. Spacing, radius and font size bind only when the value is on the scale; 12, 32 and 42 px stay unbound. Colours with no token in range stay raw and are listed in DS_GAPS.md.
Why not build in Figma first
The design system exists as code, not as a Figma library, and an earlier Figma-first rebuild had weaker structure and hover behavior than the generated preview. So the preview is the source and Figma is a copy of it.


Command and files
pnpm run figma-export projects/<project>/redesigns/<run> [--page "Fix & redesign page"]
It writes figma-export/ with install.js, chunks, assets, manifest.json, tokens.js and FIGMA_EXPORT.md. Fix differences in scripts/figma-export/, never by hand in Figma. Each pasted chunk is checksummed, because a manual paste once dropped a gradient stop that only a checksum caught.





10 / Outputs & source notes
Where the work is saved.
Each redesign run has its own output folder. The Audit Agent run and shared Design System remain separate.

  <sourceRunId>-redesign-<stamp>/
    preview-app/                 Runnable React + Vite source
    preview/verification.json    Browser checks and overall status
    preview/fidelity.json        Design and state comparison
    preview/correction-log.json  What the correction loop did
    redesign/PREVIEW.md           URL, checks and limitations
    redesign/finding-accounting.* Per-finding outcomes
    context/                     Scope, mapping, behavior, resolved
                                 targets, design baseline, budget
    figma-export/                Bundle for the Figma page
    judgments/                   Judgment answers
    review/review-index.html     Gate review links
    redesign.html                Static reference snapshot


The deliverable is preview-app/ plus its localhost URL. Failure to generate, build, serve or measure it fails R8. Static HTML is not a fallback.


Reopen or re-verify an existing preview
pnpm run agent preview <redesignRunId>
pnpm run agent preview <redesignRunId> --regenerate
pnpm run agent serve <redesignRunId> [--static]
pnpm run agent trace <redesignRunId>
pnpm run figma-export projects/<project>/redesigns/<run>
Regeneration uses saved evidence and registered decisions, and draws on the same persisted correction budget; only an explicit --reset-budget starts it over. This guide does not execute these commands.


Supported local override
Register a hand-authored section under preview-overrides/ in context/design-decisions.json. Regenerate and verify through R8; keep the override labelled.
Out of scope today
Editing the target website’s source, creating shared DS components and publishing changes are not enabled by this page route. A local proposal does not authorize those actions.
