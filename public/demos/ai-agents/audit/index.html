07 / How agents connect
How Audit Agent works
A custom TypeScript graph connects discovery, page checks, recovery and reporting. Choose a mode to follow its complete workflow.






Execution / result flowDependency or internal recovery (labelled)Human review gate




What the shared resources do


Shared DS Registry — what the design should follow. Holds your Design System’s colors, typography, components, variants and rules. It is loaded once per run and reused across page audits.


Shared Runtime Logic — how the audit works. Reusable code rules help classify elements, record results, handle uncertainty and save audit history. These resources support the agents; they are not extra autonomous agents.


Input-field example: The registry supplies the available input variants and expected styles. Runtime rules help classify a mismatch or flag uncertainty for review, then save the finding.






How matched and unmatched items move between agents
B3 partitions the detected elements into matched and unmatched groups. B4 and B5 process the matched group. B6 evaluates the unmatched group. B7 reconciles the combined outcome against an independent manifest.
These are data groups inside the sequential B-graph, not two parallel agent branches. The page session carries evidence forward; agents do not each reload the URL.


How the implementation avoids repeated work


Parallel pages
Bounded page workers
Full-site mode uses a queue. The default allows up to three browser contexts, with navigation pacing. B1–B7 remain sequential inside each worker.
Shared expectations
One registry per run
Load DS tokens, components, rules and version into a shared snapshot. Page workers reuse it instead of reading the DS independently.
Resume + reuse
Do not repeat completed work
Resume skips pages already completed in the same run. Cross-run reuse is checked after capture and requires compatible DOM, DS and policy, verified findings and passed coverage.
Targeted correction
Recheck the gap
B5/B7 reuse existing stage helpers to recover missing audit work. B7 bounds per-item attempts and overall recovery rather than restarting every check indefinitely.


See bounded parallelism
Six illustrative pages with equal work. Change worker capacity to see queue batches. This is a scheduling illustration, not measured timing or a speed benchmark.
 
Real pages have different costs. Navigation waits, dynamic content, retries and review gates affect elapsed time. No fixed speed multiplier is claimed.


Coverage recovery examples and stopping conditions
Examples highlight the relevant page agents. Recovery allows up to two attempts per item, with B7 limits of 12 rounds, 2,000 recovered captures and 15 minutes. No progress also stops recovery. Remaining outcomes must have reasons; unaccounted items keep coverage incomplete.


Retries, state and publishing are separate mechanisms
Retry: transient node failures use bounded backoff. The deterministic policy allows three total attempts; AI/hybrid allows two. Terminal errors do not retry.
State: SQLite stores run status, branch counters and gate checkpoints. This supports page-level restart and gate resume, not arbitrary recovery of every node output.
Publishing: the CLI assembles the report artifacts. Creating a local Figma plan does not mean a board has been published or verified.






08 / Read the results
Evidence becomes
a review decision.
Status explains the outcome, severity describes measured impact, and confidence expresses certainty. Read them alongside coverage.



Compliance score: MATCH ÷ (MATCH + DEVIATION + INCORRECT) × 100, with the result contract’s not-compared exclusions. Review, unverified and candidate outcomes are not automatic failures.

09 / Limits & source notes
Know what was measured.
Know what is unresolved.
The guide preserves the implementation’s limits and the saved audit’s uncertainties. It does not turn incomplete evidence into a verified result.



What the implementation does
Default checks use code and browser measurements. DS matching may use a limited approved reference catalog. B7 records coverage gaps and performs bounded recovery in no-api mode. Findings carry evidence and source references.
What still needs care
Visual judgment: the no-api semantic verdict stays NOT_CHECKED.
Reference freshness: the saved catalog does not automatically track project changes.
Dynamic content: items left unexamined after safety limits can keep coverage incomplete.
Human decisions: uncertain identity, DS governance and fix authorization still need review.
Observed evidence gap in the saved run
A finding labelled “Dealer Insights Dashboard” has an element screenshot showing a “Ken Research / Overview” bar. That image does not establish the claimed heading identity.
This guide records the limitation without rewriting the original finding or claiming the mapping is verified.
Small glossary
Node
A named pipeline responsibility, such as B3 DS Matcher.
Token
A reusable design value, such as a color or spacing variable.
Variant
A supported component treatment, such as the brand Button.
DOM / computed style
The browser’s element structure and final rendered CSS values.
Finding
A status, comparison, evidence and recommendation for an audited element.
Coverage ledger
Recorded outcomes for discovered items: audited, excluded, review, failed or unaccounted.
Deterministic
A decision made by defined code rules rather than model interpretation.
Governance proposal
A suggested DS addition, not approval or an automatic code change.
